# 专业应用开发流程

这份文档不是某一个具体项目的开发计划，而是一套可以反复复用的应用开发方法论。它的目标是帮助我从“想到哪做到哪”切换到“先定义、再拆解、再实现、再验证、再迭代”的专业工作方式。

应用开发的本质不是写代码，而是把一个真实问题变成一个可被用户使用、可被维护、可被迭代的系统。代码只是实现系统的一部分，真正重要的是：问题是否清楚、范围是否可控、结构是否合理、数据是否可靠、体验是否顺畅、上线后是否能继续演进。

## 一句话总流程

```text
问题定义
  -> 用户与场景
  -> 目标与范围
  -> 功能拆解
  -> 信息架构
  -> 交互与界面
  -> 技术方案
  -> 数据模型
  -> 开发实现
  -> 测试验证
  -> 部署上线
  -> 反馈复盘
  -> 持续迭代
```

这个流程的核心意义是：先把事情想清楚，再把事情做出来；先保证方向正确，再追求实现效率。

## 1. 问题定义

任何应用都应该从问题开始，而不是从功能开始。

很多初学者会直接说：“我要做一个 App”“我要做一个网站”“我要做一个 AI 工具”。这些都还不是清晰的问题定义。专业的第一步是回答：

- 这个应用要解决什么问题？
- 这个问题现在为什么值得解决？
- 谁会遇到这个问题？
- 这个问题发生在什么场景？
- 如果没有这个应用，用户现在怎么解决？
- 现有方案哪里不够好？
- 我做的东西凭什么有价值？

一个模糊描述：

```text
我想做一个英语学习系统。
```

一个更专业的描述：

```text
我想做一个给初中生使用的英语错题复习系统。学生可以记录错题、归类错误原因、安排复习计划，并通过统计看见自己的薄弱点。
```

后者之所以更好，是因为它说明了用户、场景、核心动作和价值。

本阶段的产出：

- 项目一句话描述
- 要解决的问题
- 目标用户
- 使用场景
- 当前替代方案
- 项目价值判断

## 2. 用户与场景

应用不是给“所有人”用的。越早期的产品，越需要明确服务哪一类用户。

例如同样是学习系统，不同用户会导致完全不同的产品：

- 学生关注做题、复习、进度、成就感。
- 老师关注班级、作业、批改、统计报表。
- 家长关注孩子是否进步、哪里薄弱、是否坚持。
- 自学者关注计划、资料、笔记、复盘、长期成长。

用户越具体，产品越容易做清楚。

分析用户时，要尽量写出真实场景，而不是抽象标签。

较弱的写法：

```text
用户需要管理学习。
```

较好的写法：

```text
用户晚上复习时，经常不知道今天该复习哪些内容，也不知道之前学过的知识哪些已经忘了，所以需要一个能记录学习内容、提醒复习、展示进度的工具。
```

本阶段要回答：

- 用户是谁？
- 用户在什么时间、地点、设备上使用？
- 用户使用前发生了什么？
- 用户打开应用后想完成什么？
- 用户完成任务后希望得到什么结果？
- 用户最容易卡在哪里？

本阶段的产出：

- 用户画像
- 使用场景
- 用户任务
- 痛点列表
- 高频操作
- 关键路径

## 3. 目标与范围

项目失败最常见的原因之一，是范围失控。

一开始什么都想做，最后很容易变成：

- 页面越来越多
- 数据结构越来越乱
- 功能之间互相影响
- 旧功能没做好，新功能又加进来
- 项目难以继续迭代

所以每个项目都要先定义版本范围，尤其是第一版。

专业做法是先做 MVP。

MVP 是 Minimum Viable Product，意思是“最小可用产品”。它不是粗糙产品，也不是半成品，而是用最小功能验证核心价值的第一版产品。

判断 MVP 的标准：

- 它能不能独立完成一个核心任务？
- 用户能不能真实使用它？
- 它能不能验证这个方向是否有价值？
- 它是不是已经去掉了非必要功能？

例如一个错题复习系统的 MVP 可以是：

- 添加错题
- 查看错题列表
- 标记掌握状态
- 按分类筛选
- 查看基础统计

第一版不一定要做：

- AI 讲解
- 拍照识别
- 班级系统
- 家长端
- 支付系统
- 排行榜

范围控制的关键句式：

```text
这个版本只解决什么问题？
这个版本明确不解决什么问题？
哪些功能留到下一版？
```

本阶段的产出：

- 版本目标
- MVP 功能范围
- 暂不做清单
- 成功标准
- 版本边界

## 4. 功能拆解

功能拆解是把抽象目标变成可执行任务。

一个专业的功能拆解通常分为三层：

```text
业务目标
  -> 用户功能
  -> 开发任务
```

例如：

```text
业务目标：帮助用户管理错题
用户功能：添加错题、查看错题、编辑错题、删除错题、筛选错题
开发任务：设计表单、创建接口、保存数据库、做列表页面、处理空状态和错误状态
```

功能可以按优先级分成：

- P0：没有它产品不能成立。
- P1：重要，但可以在核心流程稳定后做。
- P2：增强体验，可以后续迭代。
- P3：想法不错，但当前不做。

功能拆解时要避免只写名词，要写成用户动作。

较弱的写法：

```text
错题管理
学习统计
用户系统
```

较好的写法：

```text
用户可以添加一条错题。
用户可以查看自己的错题列表。
用户可以按分类筛选错题。
用户可以看到本周新增错题数量。
用户可以登录后保存自己的数据。
```

本阶段的产出：

- 功能清单
- 优先级
- 用户故事
- 验收标准
- 任务拆解

## 5. 信息架构

信息架构决定应用有哪些页面、模块和导航方式。

如果信息架构混乱，用户会不知道去哪里，开发者也会不知道代码如何组织。

常见页面结构包括：

- 登录页
- 首页或仪表盘
- 列表页
- 详情页
- 新建或编辑页
- 统计页
- 设置页
- 管理后台

设计信息架构时，要先画出应用地图。

示例：

```text
首页
  -> 今日任务
  -> 学习统计
  -> 最近记录

错题
  -> 错题列表
  -> 错题详情
  -> 添加错题
  -> 编辑错题

复习
  -> 今日复习
  -> 复习记录

设置
  -> 个人资料
  -> 数据管理
```

信息架构要回答：

- 应用有几个主模块？
- 用户最常访问哪个模块？
- 哪些页面需要放在一级导航？
- 哪些页面只是流程中的子页面？
- 用户从一个页面到另一个页面是否自然？
- 空数据时用户应该看到什么？

本阶段的产出：

- 页面清单
- 应用地图
- 导航结构
- 页面之间的跳转关系
- 每个页面的核心任务

## 6. 用户流程

用户流程是用户完成一个目标时经过的步骤。

功能清单回答“有什么”，用户流程回答“怎么用”。

例如添加错题的流程：

```text
进入错题列表
  -> 点击添加
  -> 填写题目内容
  -> 选择科目和分类
  -> 填写错误原因
  -> 保存
  -> 返回列表
  -> 新错题出现在列表中
```

专业流程设计不仅考虑成功路径，还要考虑异常路径。

成功路径：

```text
用户填写完整信息 -> 保存成功 -> 页面更新
```

异常路径：

```text
用户没填必填项 -> 显示校验提示
网络请求失败 -> 显示错误信息并允许重试
用户误点取消 -> 确认是否放弃编辑
保存过程中 -> 禁用重复提交
```

本阶段要回答：

- 用户完成核心任务需要几步？
- 是否有不必要的步骤？
- 每一步需要什么信息？
- 系统在每一步给什么反馈？
- 失败时用户怎么恢复？

本阶段的产出：

- 核心用户流程
- 成功路径
- 异常路径
- 状态反馈
- 边界情况

## 7. 交互与界面设计

界面设计不是装饰，而是帮助用户理解和行动。

一个应用页面通常要关注：

- 信息层级是否清楚
- 主要操作是否突出
- 次要操作是否克制
- 表单是否容易填写
- 列表是否容易扫描
- 状态是否有反馈
- 错误是否可理解
- 移动端是否可用
- 文案是否准确

常见状态必须提前设计：

- 默认状态
- 加载状态
- 空状态
- 成功状态
- 错误状态
- 禁用状态
- 编辑状态
- 删除确认状态

例如错题列表页面，不只是显示列表，还要考虑：

- 没有错题时显示什么？
- 正在加载时显示什么？
- 加载失败时怎么重试？
- 搜索没有结果时如何提示？
- 删除前是否确认？
- 数据很多时是否分页？

界面设计的核心不是“好看”，而是“清楚、稳定、可信、好用”。

本阶段的产出：

- 页面草图
- 组件清单
- 状态清单
- 表单字段
- 操作文案
- 响应式布局规则

## 8. 技术方案

技术方案要服务项目目标，而不是为了使用某个新技术。

技术选型时要考虑：

- 项目规模
- 开发者能力
- 是否需要登录
- 是否需要数据库
- 是否需要实时能力
- 是否需要 AI 能力
- 是否需要移动端
- 是否需要多人协作
- 部署是否简单
- 后续维护成本

常见技术组合：

```text
静态网站：
HTML + CSS + JavaScript

前端应用：
React 或 Vue + Vite

全栈 Web 应用：
Next.js / Nuxt + 数据库

后端 API：
Node.js / Python / Java / Go

数据库：
SQLite / PostgreSQL / MySQL / MongoDB

AI 应用：
前端 + 后端 + AI API + 数据库 + 文件处理
```

初学和个人项目最重要的是：技术栈不要过度复杂。

一个合理的学习路线：

```text
静态页面
  -> 前端交互
  -> 前端工程化
  -> 后端接口
  -> 数据库
  -> 登录认证
  -> 部署上线
  -> AI 能力
```

本阶段的产出：

- 技术栈选择
- 前端方案
- 后端方案
- 数据库方案
- 部署方案
- 第三方服务清单
- 技术风险

## 9. 数据模型

数据模型是应用的骨架。

很多项目后期难以迭代，不是因为页面写得不好，而是因为数据结构一开始没有想清楚。

设计数据模型时要回答：

- 系统里有哪些核心对象？
- 每个对象有哪些字段？
- 对象之间是什么关系？
- 哪些数据必须长期保存？
- 哪些数据只是临时状态？
- 哪些字段需要唯一？
- 哪些字段需要索引？
- 删除数据时是否保留历史？

例如学习系统可能有这些对象：

```text
用户 User
学习记录 StudyRecord
错题 Mistake
复习记录 ReviewLog
标签 Tag
项目 Project
```

对象之间的关系：

```text
一个用户有多条学习记录。
一个用户有多个错题。
一个错题可以有多个复习记录。
一个错题可以有多个标签。
```

简单字段示例：

```text
Mistake
- id
- user_id
- title
- content
- subject
- category
- wrong_reason
- status
- created_at
- updated_at
```

本阶段的产出：

- 核心实体
- 字段设计
- 表关系
- 数据生命周期
- 数据权限
- 初版数据库结构

## 10. API 与业务逻辑

如果应用有后端，就需要设计 API。

API 是前端和后端之间的契约。契约越清楚，开发越稳定。

常见 API 示例：

```text
POST /api/auth/register
POST /api/auth/login
GET /api/mistakes
POST /api/mistakes
GET /api/mistakes/:id
PUT /api/mistakes/:id
DELETE /api/mistakes/:id
GET /api/stats
```

设计 API 时要明确：

- 请求方法
- 请求路径
- 请求参数
- 返回数据
- 错误格式
- 权限要求
- 是否分页
- 是否支持筛选和排序

业务逻辑要放在合适的位置。

例如：

- 表单格式校验可以在前端先做。
- 权限校验必须在后端做。
- 密码加密必须在后端做。
- 重要数据写入必须由后端控制。
- 统计计算可以由后端统一生成。

本阶段的产出：

- API 清单
- 请求和响应格式
- 权限规则
- 错误码
- 业务规则
- 接口文档

## 11. 开发实现

开发不是随意写文件，而是按模块逐步实现。

推荐实现顺序：

```text
搭建项目结构
  -> 建立基础页面
  -> 建立数据模型
  -> 实现核心接口
  -> 实现核心页面
  -> 接通前后端
  -> 完善状态和错误处理
  -> 补充测试
  -> 优化体验
```

开发时要遵守几个原则：

- 每次只做一个明确的小任务。
- 先完成核心路径，再补边界体验。
- 每完成一个功能就运行和验证。
- 不在同一轮里混入无关重构。
- 能复用已有模式，就不创造新模式。
- 文件结构要为后续维护服务。

一个功能的开发闭环：

```text
明确需求
  -> 找到相关文件
  -> 写最小实现
  -> 本地运行
  -> 手动验证
  -> 补测试或检查清单
  -> 记录变更
```

本阶段的产出：

- 可运行代码
- 页面实现
- 后端接口
- 数据库迁移
- 测试用例
- README 或开发说明

## 12. 测试验证

测试的目的不是证明自己写对了，而是主动寻找哪里可能出错。

常见测试层级：

- 手动测试：像真实用户一样使用。
- 单元测试：测试独立函数或逻辑。
- 接口测试：测试后端 API 是否符合约定。
- 端到端测试：模拟完整用户流程。
- 视觉检查：检查页面布局是否正常。
- 回归测试：确认新功能没有破坏旧功能。

每个功能至少要验证：

- 正常情况能否完成。
- 必填项为空时是否有提示。
- 网络失败时是否有反馈。
- 没有数据时是否有空状态。
- 数据很多时是否还能正常显示。
- 用户没有权限时是否被拦截。
- 刷新页面后状态是否合理。

例如添加错题功能的验收清单：

```text
- 可以打开添加页面。
- 必填项为空时不能提交。
- 填写完整后可以保存。
- 保存成功后列表出现新错题。
- 保存失败时显示错误提示。
- 重复点击保存不会产生重复数据。
- 取消编辑时不会误保存。
```

本阶段的产出：

- 测试清单
- 测试用例
- 已知问题
- 修复记录
- 验收结论

## 13. 部署上线

本地能运行，不代表产品完成。真正的应用要能被用户访问。

部署前要检查：

- 构建是否成功
- 环境变量是否配置
- 数据库是否可连接
- 登录和权限是否正常
- 静态资源是否正常加载
- API 地址是否正确
- 错误日志是否可查看
- 是否启用 HTTPS

常见部署方案：

```text
前端：
Vercel / Netlify / Cloudflare Pages / GitHub Pages

后端：
Render / Railway / Fly.io / 云服务器 / Cloudflare Workers

数据库：
Supabase / Neon / Railway PostgreSQL / 云数据库
```

部署不是一次性动作，而是上线流程的一部分。

上线后要保留：

- 线上地址
- 部署平台
- 构建命令
- 环境变量说明
- 数据库位置
- 回滚方法
- 常见故障处理

本阶段的产出：

- 可访问的线上应用
- 部署说明
- 环境变量清单
- 上线检查清单
- 回滚方案

## 14. 反馈与复盘

产品上线后，真正的学习才开始。

要观察：

- 用户是否能完成核心任务？
- 哪一步最容易卡住？
- 哪些功能没人用？
- 哪些功能被频繁使用？
- 用户提出的问题是否集中？
- 数据是否证明产品有价值？
- 下一版最应该改什么？

复盘不是责备自己，而是让下一轮更清楚。

每次迭代后可以记录：

```text
这次做了什么？
原本目标是什么？
实际完成了什么？
哪里比预期顺利？
哪里比预期困难？
发现了什么认知问题？
下一次如何改进流程？
```

本阶段的产出：

- 用户反馈
- 数据观察
- 问题列表
- 复盘记录
- 下一版计划

## 15. 迭代管理

应用开发不是一次性完成，而是持续演进。

一个健康的迭代节奏：

```text
确定下一版目标
  -> 选择少量高价值任务
  -> 明确不做什么
  -> 实现和验证
  -> 发布
  -> 复盘
```

版本示例：

```text
V0.1：能完成核心任务
V0.2：补齐关键体验
V0.3：加入统计和筛选
V1.0：稳定上线版本
V1.1：根据反馈优化
V2.0：扩展新模块
```

迭代时要避免两个问题：

- 没有完成旧功能，就不断加新功能。
- 没有验证真实价值，就不断优化细节。

每一版都要有明确主题。

较弱的版本目标：

```text
这一版优化一下。
```

较好的版本目标：

```text
这一版让用户可以稳定完成添加、查看、复习错题的核心流程。
```

本阶段的产出：

- 版本路线图
- 当前版本目标
- 下一版任务
- 暂缓任务
- 发布记录

## 做项目时的核心检查清单

开始前：

- 我是否清楚这个项目解决什么问题？
- 我是否知道第一版服务谁？
- 我是否能说出第一版只做什么？
- 我是否写下了暂时不做什么？
- 我是否画出了页面结构？
- 我是否想清楚了核心数据？

开发中：

- 我现在做的任务是否属于当前版本？
- 我是否一次只改一个明确目标？
- 我是否在完成核心路径后再做细节？
- 我是否处理了加载、空状态、错误状态？
- 我是否验证了功能真的可用？

发布前：

- 核心流程是否完整跑通？
- 页面刷新后是否正常？
- 权限和数据是否安全？
- 移动端是否可用？
- 构建是否成功？
- 线上环境变量是否正确？

发布后：

- 用户是否能完成核心任务？
- 哪些地方让用户困惑？
- 哪些功能值得保留？
- 哪些功能应该删掉或推迟？
- 下一版最重要的一件事是什么？

## 我对这个知识库的使用原则

这个 Web coding 学习库不是项目代码库，而是做事方法论和学习认知库。

它应该保持干净：

- 不放具体应用项目的业务代码。
- 不混入某个产品的临时实现细节。
- 不把多个项目的杂乱任务堆在一起。
- 只沉淀可复用的流程、原则、模板、复盘和认知。

具体项目应该在单独的新项目中完成。这个库负责回答：

```text
我应该如何思考？
我应该如何拆解？
我应该如何执行？
我应该如何检查？
我应该如何复盘？
```

当具体项目遇到混乱时，回到这里，用流程重新整理。

## 与 Project Kickoff Skill 的关系

这份文档适合人阅读、学习和复盘，它解释了为什么要这样做，以及每个阶段背后的专业逻辑。

`project-kickoff` Skill 适合在真正启动项目时使用，它会把这套方法压缩成可执行流程，帮助我在写代码前完成：

- 想法澄清
- 用户与场景定义
- MVP 收敛
- 不做清单
- 项目启动文档
- 开发阶段拆解
- 验收标准

两者的分工是：

```text
专业应用开发流程.md
  -> 用来学习、理解、复盘、持续完善方法论

project-kickoff Skill
  -> 用来在新项目对话中直接执行这套方法
```

以后开始新项目时，可以在新对话中说：

```text
请使用 project-kickoff skill，先帮我把这个想法整理成项目启动文档。不要急着写代码，先完成问题定义、目标用户、MVP、第一版不做清单、页面结构、数据对象和开发阶段拆解。
```

## 最重要的认知

专业开发不是“想到功能就写功能”，而是：

```text
先定义问题，再定义用户；
先控制范围，再设计功能；
先设计结构，再进入实现；
先验证核心流程，再追求完整体验；
先复盘问题，再开始下一轮迭代。
```

这个流程的价值不是让开发变慢，而是让每一步都更有方向。真正专业的人，不是写得更快，而是更少在错误方向上消耗时间。
